First, understand the finding

A database table stores records; a SQL query selects them. In this example, SELECT id, username FROM users WHERE username = 'alice' returns Alice. The vulnerable code joins a username directly into SQL, so specially formed input can alter the query instead of remaining ordinary data.

Review the core concepts

SQL injection: untrusted input is interpreted as part of a database instruction. The classroom input ' OR 1=1 -- illustrates how an always-true condition could change the result; this page uses a prepared simulation and does not execute SQL.

Parameterized query: keep the SQL structure fixed with a ? placeholder and bind the username separately, such as conn.execute(query, (username,)). The SQLite driver treats the value as data.

Review principle: a scanner alert and an AI-suggested patch are candidates for investigation, not proof. Test expected lookups and edge cases, inspect the change, and use human review before merging.

Regression examples: known users, an unknown username, the supplied injection example, and legitimate punctuation such as O'Reilly.

Evaluate security effectiveness
Compare detection quality and remediation time using invented classroom data—not product performance claims.
HYPOTHETICAL BENCHMARK
Know what the measures mean
True positive (TP): a real vulnerability reported by the tool.
False positive (FP): a reported issue that is not actually a vulnerability.
False negative (FN): a real vulnerability the tool missed.
Precision = TP ÷ (TP + FP): how trustworthy reported alerts are.
Recall = TP ÷ (TP + FN): how many real vulnerabilities were detected.
F1 balances precision and recall. MTTR is the mean time to remediate; include testing and review consistently.
A faster process is not automatically safer. Also compare fix reliability, regressions, review effort, and cost.
