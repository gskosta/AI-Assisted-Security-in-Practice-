01 · Introduction

How can a username change a database query?

Your goal: identify an SQL injection weakness, inspect a suggested repair, test its behaviour, and make a review decision.

A vulnerability is a weakness that could be exploited. SQL injection happens when untrusted input becomes part of an executable database instruction.

Database and table
A database stores information. A table organises records into rows and columns. Our fictional users table contains (1, alice) and (2, bob).
SQL query
An instruction to a database. SELECT chooses columns, FROM names the table, and WHERE limits which rows match.
SELECT id, username FROM users WHERE username = 'alice'

Read this as: “Return the ID and username for rows whose username is alice.” Text values appear inside quotes.

The unsafe pattern

query = "SELECT id, username FROM users WHERE username = '" + username + "'"

The + joins text. Joining user input directly into SQL lets special input change the instruction.

Worked example: the input ' OR 1=1 -- closes the quoted text, adds an always-true condition (1=1), and starts a comment with --. In our prepared example, the query matches both users.

The secure pattern

query = "SELECT id, username FROM users WHERE username = ?"
conn.execute(query, (username,))

A parameterised query sends SQL instructions and input values separately. The SQLite driver treats the entire username as a value. The ? is its placeholder; other drivers may use different ones. The comma in (username,) creates a one-item Python tuple.

Code scanning alert
A scanner’s report of a possible weakness. A developer investigates the evidence.
Suggested patch and diff
A patch is a proposed change. A diff shows removed lines with − and added lines with +.
Regression test
A check that a change preserves intended behaviour. Security regression tests can also check that a previously demonstrated attack no longer works.

Remember: AI can suggest a repair. The developer still checks the root cause, tests functionality, and reviews the change.

01 · Introduction

How do we know a security tool helps?

Your goal: distinguish false alarms from missed vulnerabilities, calculate detection metrics, and compare repair time without ignoring quality.

Imagine an instructor has a set of code examples whose vulnerabilities have already been confirmed. We compare a tool’s findings against that known reference. Reporting more findings does not automatically make a tool better.

True positive (TP)
The tool reports a vulnerability, and it is genuinely present.
False positive (FP)
The tool reports a vulnerability, but investigation shows harmless code: a false alarm.
False negative (FN)
A real vulnerability exists, but the tool misses it.
Worked example: 10 alerts are reported. Eight are real, and two are false alarms. The dataset also contains two real vulnerabilities the tool missed. So TP = 8, FP = 2, and FN = 2.
Precision · How trustworthy are the reported alerts?
TP ÷ (TP + FP). Here: 8 ÷ 10 = 80%. It considers all reported alerts.
Recall · How many real vulnerabilities were caught?
TP ÷ (TP + FN). Here: 8 ÷ 10 = 80%. It considers all actual vulnerabilities, including missed ones.
F1 · How do precision and recall balance?
Their harmonic mean: 2TP ÷ (2TP + FP + FN). Here it is 80%. A strong F1 does not prove a generated patch is correct.
Mean time to remediate (MTTR) · How long do fixes take?
Add remediation times and divide by the number of resolved findings. For 4, 8, and 12 hours: (4 + 8 + 12) ÷ 3 = 8 hours. Define the same start/end points for both processes and include review and testing.

Dropping from 16 to 8 hours means a 50% reduction in average repair time. Compare similar findings and check repair reliability, regressions, human review effort, and cost.
